Arbiter

A governed agentic workflow system. Claude acts as a structured team of department heads — each with a defined role, clear standards, and a handoff contract to the next. You stay in the loop at every approval checkpoint.

What is Arbiter

Claude without structure is a general assistant. Every session starts cold. Outputs drift based on how a question is phrased. Context disappears at the end of a conversation, and the next session spends its first ten minutes reconstructing what the last one already knew.

Arbiter solves this by giving Claude three things it doesn't have by default: a defined role for each phase of work, state that carries forward through a knowledge vault, and standards that apply to every word and every line of code.

The result is a session-to-session thinking partner that knows your stack, your clients, your standards, and what happened on the last ticket — without you recapping any of it.

What it is

A structured skill chain

Claude Code skill files that turn Claude into specialized roles: intake coordinator, diagnostician, architect, engineer, adversarial reviewer. Each role has a defined job and a clean handoff to the next.

What it is not

An autonomous agent

Nothing runs without you invoking it. Nothing posts to Jira, sends a Slack message, or commits code. Every output is a draft. The gates in each skill are where your judgment replaces Claude's.

How It Works

State That Carries Forward

Every skill writes a state file to your knowledge vault at 02-tickets/{KEY}/{KEY}-state.md. The next skill reads it. When /{prefix}-dev starts, it already knows the root cause, the approved design, and every open assumption — you never recap. A session can end and pick up the next day without losing a single decision.

Standards Applied Everywhere

Three documents govern all output. Every skill reads them at Step 0, before producing anything.

StandardGoverns
voice-standard.mdEvery word. Conclusion first, bracket test (cut anything that can be removed without losing meaning), active voice, no template residue. Applies to a Jira comment and a system design doc equally.
technical-standards.mdEvery line of code. Type hints, functions at 40 lines or fewer, named constants, no secrets, explicit write modes and null handling. Verify before using any method or path.
pipeline-standards.mdEvery pipeline. Layer boundaries, write semantics, idempotency at every layer, null handling explicit at every join, schema lineage from source through silver.

The Session Frame

/start opens every work block with a Jira sync, vault health check, and open blocker list — you see the full picture before picking up anything new. /close writes the session log, updates the ticket state file, and surfaces corrections as memory candidates. Nothing is left floating between sessions.

Memory

When you correct Claude's approach, /close surfaces it as a memory candidate. You approve it. It saves to memory/ in the repo. The next session, the correction applies without you repeating it. Memory files compound over time into a picture of how you work, what has gone wrong, and what has been validated.

Prerequisites

Complete this before running the installer. Expected time: 25–30 minutes the first time, mostly waiting for downloads and token collection.

Applications

  • Homebrew (macOS) or apt/dnf/pacman (Linux) — package manager for everything below
  • Git — configured with your name and email. Verify: git config --global user.name
  • Node.js 18+ — MCP servers run via npx. Verify: node --version
  • Python 3.9+ — required for the vault search pipeline. Verify: python3 --version
  • Claude Code — authenticated with a Claude.ai subscription or Anthropic API key. Download: claude.ai/download
  • VSCode with the Claude Code extension installed (Cmd+Shift+X → search "Claude Code")
  • Obsidian — for your knowledge vault. Download: obsidian.md

Installation

The installer collects your identity, creates the vault folder structure, installs skill files, stores tokens securely, wires MCP servers, and builds the initial vault search index. Python packages (chromadb, sentence-transformers) install automatically.

  1. 1

    Clone the repo

    Use the naming pattern {base}/{prefix}-dotfiles. Your prefix drives all folder names, environment variables, and slash command names.

    bash
    # Example: base folder "dipen", prefix "ah"
mkdir -p ~/Developer/dipen
git clone <repo-url> ~/Developer/dipen/ah-dotfiles
cd ~/Developer/dipen/ah-dotfiles
  2. 2

    Run the installer

    Walks you through prompts for name, title, company, domain, prefix, and service connections. If you have an existing Claude Code setup it detects it automatically and offers a migration path — your memory files and custom skills are preserved, standard skills are updated, and your entire ~/.claude/ is backed up before any change.

    bash
    ./install.sh
  3. 3

    Reload your shell and verify

    The installer writes environment variables to your shell profile. Reload it, then verify the vars are set. Your prefix uppercased becomes the env var prefix: prefix ah gives $AH_KNOWLEDGE.

    bash
    source ~/.zshrc

echo $AH_KNOWLEDGE    # → ~/Developer/dipen/ah-knowledge
echo $AH_SCRIPTS      # → ~/Developer/dipen/ah-scripts
echo $CLAUDE_DOTFILES # → ~/Developer/dipen/ah-dotfiles
  4. 4

    Connect MCP servers in VSCode

    Open VSCode → Claude Code panel → settings gear → MCP Servers → Connect next to each server. The Atlassian server opens a browser window for OAuth on first connect. Verify by typing @jira or @slack in Claude Code — tool autocomplete appears if the server is live.

  5. 5

    Open your vault in Obsidian and start

    Obsidian → Open folder as vault → select ~/Developer/dipen/ah-knowledge. All subfolders are already created. Then in Claude Code:

    claude code
    /start

Vault search is automatic

Every prompt is automatically searched against the vault index by hooks/vault_search_hook.sh. Relevant documents appear in the conversation as a <vault_context> block. Re-index after adding new documents: python3 $CLAUDE_DOTFILES/rag/build_index.py --dir $AH_KNOWLEDGE --index $AH_KNOWLEDGE/.rag_index

Walkthrough: A Bug Ticket

A client reports 22 patients are missing from the monthly TAVR clinical report. The submission was two weeks ago. You open Jira and find ticket CD-200. Here is how the chain works on a real ticket.

Fictional data

All client names, ticket IDs, table names, and data values are fictional. The full worked example with code output is in docs/walkthrough.md.

/start
Jira syncs. You see 3 open tickets, vault health for 12 state files, and one stale state file. CD-200 is flagged high priority. You start there.
/ah-ticket CD-200
The skill reads Jira, pulls the Lakewood Health client file from the vault's system map, and produces an ORIENT block: what is confirmed (500 records submitted, 478 in clinical report, pipeline ran without error), what is unknown (where the 22 dropped), and what is assumed. The explain-back gate fires — you state your read of the ticket in two sentences before the skill accepts the classification and routes to /ah-support.
/ah-support CD-200
The diagnostician traces Raw → Bronze → Silver. Raw: 500 rows confirmed. Bronze: 478 rows. Gap appears at Bronze. A null check on Raw reveals 22 records where encounter_date IS NULL. The Bronze transform filters them at line 47: df.filter(col("encounter_date").isNotNull()). Root cause confirmed. The handoff package names three fix options and flags that the filter was added by a prior Data Platform decision — any change requires their review.
/ah-spec CD-200
The spec skill reads the support handoff — not Jira — and restates the problem before writing a single requirement. Four requirements, four acceptance criteria with pass/fail conditions, two success metrics. AC1: zero records dropped silently at Bronze. AC2: a quarantine_ind column exists on Bronze with value 1 for null records. Pass condition is explicit.
/ah-arch CD-200
Three design options. Option A recommended: add quarantine_ind = 1 to Bronze records with null encounter_date, exclude them at Silver, alert client to resubmit. Option B (coalesce to load_date) rejected — a synthetic date is wrong data, and wrong data is worse than flagged data. Option C (pass through naked) rejected — downstream date range logic produces unpredictable results on nulls. The original filter existed for this reason.
◆ You approve Option A
You post the design to Jira for Data Platform review. They respond the same day: approved. Implementation is now unlocked.
Gate cleared
/ah-dev CD-200
The TEACHING gate fires — you explain the approach before code is written. The skill produces the Bronze and Silver changes: typed functions, named constants (NULL_ENCOUNTER_DATE_FLAG: int = 1), file header with ticket reference, logging via the proper framework, no magic numbers.
/ah-qa CD-200
The adversary reads spec, design, and implementation. One HIGH finding: the Silver filter uses == 0 comparison on the integer flag without an explicit cast — if quarantine_ind is coerced to string anywhere in the pipeline, the filter fails silently and all records are excluded. One MEDIUM: no alert when the entire batch is quarantined. Both valid. HIGH routed back to /ah-dev. MEDIUM deferred to a follow-on ticket by mutual agreement.
◆ QA approved with conditions
HIGH finding fixed. QA re-runs and approves. You run /draft for the Jira resolution comment (internal voice) and the client Slack message (client voice: "Your TAVR data is complete. 22 records from your May submission are held for correction.").
Gate cleared
/close
Session log written to the vault. State file updated to CLOSED. Memory candidate surfaced: quarantine_ind is the standard column name for null-excluded records at Bronze — not filter_ind or exclude_ind. You approve it. The next session will apply this without you repeating it.

Nine skill invocations across two or three sessions. Your judgment at every gate. Nothing sent automatically. The 22 missing patients have a clear resolution path and the system carries a memory of how this class of problem was handled.

Key Concepts

PHI Guardrails

Health data rules apply at every layer — code, logs, tests, configs, commits, vault files, and drafts. The moment PHI comes into scope, the skill stops and flags it. You acknowledge before anything continues.

Never appears in any output: patient names, MRNs, dates of birth, encounter IDs that could identify a person, any field that uniquely identifies a patient.

Permitted: counts ("22 of 500 records failed the null check"), aggregate statistics, anonymized field references, severity classifications.

Two Voices

Every communication is labeled before it is drafted. Client voice speaks in outcomes — the reader is a clinical administrator who cares about data delivery and what they need to do, not pipeline internals. Internal voice is technical and precise — table names, ticket numbers, failure counts, specific ownership of next steps, no softening. The same root cause produces two different messages. You choose which one to send and when.

The Decision Framework

Every nontrivial design decision produces four pieces before anything is acted on: WHAT is being decided, HOW the approach works, WHY this approach was chosen, and WHY NOT the alternatives — named and rejected, with reasons. Presenting one option without naming what was considered is not a decision. It is a suggestion. The framework forces the work to show and gives you something concrete to correct.

The Vault

The vault is your personal knowledge base, backed by Obsidian and git. Skills depend on it. The system map at 01-system-map/ holds client files, pipeline files, architecture docs, and schema knowledge. When /{prefix}-ticket orients on a client ticket, it reads the client file here. When /{prefix}-support traces a bug, it checks the pipeline file. Without the system map, every investigation starts from scratch.

Reusable Scripts

The ${PREFIX}_SCRIPTS folder stores scripts Claude generates for recurring tasks. If Claude writes a Python or bash script for a task and the same task comes up again, it runs the saved file instead of regenerating code or making a new API call. Scripts accumulate into a typed, audited library — each following the coding standards: type hints, named constants, file header with ticket reference.

Adapting the System

Arbiter was built for a specific context — data integration at a health AI company working with Databricks, Delta Lake, and Unity Catalog — but most of it is universal. The voice standard, the decision framework, the skill chain model, the session frame, and the memory feedback loop transfer to any domain without changes. The pipeline standards and skill implementations reference specific tables and catalog names — adapt those to your stack. Start with CLAUDE.md: fill in your role, your stack, and your domain. The behavior rules and guardrails below that section take effect immediately.
